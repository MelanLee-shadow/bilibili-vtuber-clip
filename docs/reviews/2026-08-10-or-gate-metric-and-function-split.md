## 一、Pro 顺手抓到的一个算术疑点（已核实：不是缺陷）

Pro 按我给的维度分算出四条的 raw 应是 `77.5 / 76.25 / 77.5 / 72.5`，而我报的是
`75.5 / 72.25 / 70.5 / 69.5`，于是要求先钉死"要么你给的是 effective、要么实现有算术错误"。

**核实结果：我给的是 effective，Pro 反推的惩罚 `2 / 4 / 7 / 3` 与 free 上真实的

## 二、OR 门：结论与结构

**裸 `max(单维分数)` 是错的；`softmax`/p-范数伪装成 OR 也是错的。**
正确形态是**语义路径 OR**，不是维度 OR：

```
硬门槛 ⟶ 若干"命名卖点路径"各自评分 ⟶ 取 max ⟶ 题材疲劳惩罚

Q = max( P_broad − U_broad ,  max_j( P_j − U_j ) )
E = Q − U_global − F(topic_fingerprint)
```

- `P_broad`：保留旧的"多项都不错"综合路径（把 `self_contained` 排除后重新归一化）。
- `P_j`：关系 / 立场 / 观众驱动 / 反差 / 笑点 各自一条独立卖点路径。
- `self_contained` 放**最前面当 gate**，不参与 OR——它是必要条件不是卖点。
- `lidousha_centrality` **不适合当独立卖点**，宜作加分项或归属条件：
  "她是主角"本身不构成值得发布的理由。

### 关键机制：`level=4` 只是主张，不是通行证

Pro 的核心设计是 **StandaloneProof 证据合同**——某一轴打到 4 只是*声称*，
必须通过该轴专属的证据合同才成为可以触发 OR 的 `verified_level_4`：

- **证据可定位**：引文或视觉事件必须落在候选片段时间范围内；重复引用同一句话不算两份。
- **事件闭合**：至少满足其一 ——（a）一条完整的"动作/发言 → 对方反应或结果"链；
  （b）两个不重叠的独立证据原子。
  （这样不会因为强求"两段证据"而误杀一个本身完整的单一高潮。）

**并且：证据不足不是"减 3 分"，而是路径不成立。** 对单轴放行路径，证据是成立条件不是软加减项。

### 惩罚项放在哪（Pro 明确点出的陷阱）

**路径相关的不确定性必须在取 max *之前*、在各路径*内部*扣**，且只惩罚该路径实际依赖的证据。
把七个维度的不确定性先加总、再从 max 之后扣——**会让落败轴的噪声污染获胜路径**。
疲劳惩罚 `F` 是"组合选择效用"不是片子自身质量，放在最后全局扣。

### 对抗性回归（Pro 给的清单，直接可用）

| 变形 | 预期 |
|---|---|
| 把任意一项人工篡改为 4、但不给证据合同 | 不得激活 OR |
| 同一时间戳证据复制两次 | 不算两份证据 |
| 引文落在片段范围外 | 路径失效 |
| `self_contained` 改为 1 | 无论其他分多高都不得发布 |
| 关系分 4 但仅靠 CP lore | 关系路径失效 |
| 获胜轴 4→3 | 对应突出路径必须关闭 |
| 非获胜轴不确定性增加 | 不得降低当前获胜路径分 |
| 疲劳标签换成较轻类别（语义标签未变） | 不得规避惩罚 |

## 三、Pro 对"给游戏场单独配分数门"的否决

# 问题 2：`_stage_publish_draft`（597 行）

## 结论：**拆，而且现在就作为专门拆解任务处理**

Pro 明确说这不是"597 是否超过某个审美阈值"的问题，决定性证据是：

- 已经**第二次**上调债务数字；
- 一年前留下明确治理约束「下次动必须先拆」；
- 本次又 578 → 597；
- 函数**同时承担**模式决策、内容生成、外部副作用、证据绑定、最终 fail-closed；
- 40 个分支 + ~130 个局部名 = **一个隐式状态机**；
- 模块本身也已超 2000 行。

**"增长来自分支合并而不是新功能"不构成不拆的理由**——它只解释代码从哪来，
不改变主干当前承担的风险。

## 怎么拆（以及**不要**怎么拆）

**❌ 不要按四种投稿模式复制四套函数**（`_publish_new` / `_publish_same_bv_repair` /
`_publish_replay` / `_publish_manual_authorized`）。那会复制标题、封面、证据验证与提交逻辑，
**随后某个 fail-closed 修复只补了三种模式、第四种遗漏，风险更高**。
四种模式应先变成**显式策略/状态输入**，由一次规划过程解释。

**✅ 三处切口**：
1. `resolve_publish_plan(request, observed_state) → 不可变 DraftPlan`
   ——尽量纯计算：不生成封面、不写文件、不提交草稿。
   风险：当前函数里可能有"读文件后顺便决定策略"的隐式逻辑，抽取时容易漏。
   控制：`DraftPlan` 绑定输入快照/artifact identity，最终 commit 前重新验证关键状态。
2. 封面路由做成**独立的副作用边界**。
3. 证据封装 + 原子提交做成**终端阶段**。

## 130 个局部变量

**是，比"597 行"更值得警惕**——但真正的问题不是数字，而是**这些变量跨越了多少阶段和失败域**。

⚠️ **不要**用一个 `PublishContext` 大包把 130 个局部变量变成 130 个可变字段——
那只是把"局部变量问题"升级成"共享可变状态问题"。阶段输出应当是小型、不可变、语义明确的数据结构。

## 🔴 最该防的那一种做砸方式

**在 helper 边界上合并失败语义，把原来的 fail-closed 变成 fallback 或部分成功。**

典型：
```python
try:
    cover = prepare_cover(...)
except Exception:
    cover = fallback_cover(...)
```
如果 `prepare_cover()` 内部可能抛出服务超时 / 授权无效 / 哈希不匹配 / 回执缺失 / 文件损坏，
那么**一次看似合理的提取就让安全失败走进了普通降级路线**。

防线：
- **失败类型分层**：只有白名单里的 recoverable 错误允许 fallback；
- **使无效状态不可表示**：commit 只接受 `SealedDraft`，不接受一堆布尔与可选字段；
- **差分测试新旧实现**：固定 fixture/时钟/随机源/模拟外部系统，比较返回值、异常类型、
  是否创建草稿、外部调用及顺序、文件与哈希、**重放第二次的行为**；
- **负路径优先**：每个 fail-closed gate 至少一个独立失败测试，并断言无不可逆副作用；
- **先行为保持，后功能改动**：拆分提交里不顺便"清理逻辑/改 fallback/简化授权"；
- **禁止宽泛捕获跨越安全边界**：orchestrator 不应有覆盖整个阶段的 `except Exception`。

## 验收判据（Pro 给的，可直接当拆解任务的完成定义）

- 4 种模式 × 4 种封面路线全部有显式测试；
- 所有非法组合在**不可逆副作用之前**失败；
- 每个 fail-closed gate 有负向测试；
- 只有明确的 cover recoverable failure 能进入 cover fallback；
- 新旧实现 fixture 差分一致；
- 重放两次不产生重复不可逆效果；
- 原 orchestrator **明显低于 300，建议低于 120**；
- 没有新建 300 行以上 helper；
- **原模块净下降**，不是只把函数改名或塞进类里；
- 欠账账本数字**下降**，不再批准 597 作为新基线。

## Pro 自陈最没把握

- 未见源码/调用图/副作用顺序，无法确定**标题生成**该归规划阶段还是内容物化阶段；
- 无法确定代码迁出原模块后是否产生**循环依赖**，模块切口可能要围绕现有类型所属位置微调。

但「必须拆」「不能按四种模式复制」「必须保护异常语义与最终证据封装」这三条，Pro 把握很高。
