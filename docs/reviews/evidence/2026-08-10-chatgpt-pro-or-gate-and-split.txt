2. 如何区分“单轴出色”和“单轴刷分”

核心原则是：

level=4 只是主张；只有通过该轴的证据合同后，才成为可以触发 OR 的 verified_level_4。

不要把证据不足仅仅处理成“减 3 分”。对于单轴放行路径，证据是成立条件，不是软加减项。

建议的数据结构

每一个准备触发 OR 的高分轴都必须附带：

StandaloneProof
- axis
- claim
- evidence_atoms[]
  - start_ms
  - end_ms
  - exact transcript quote and/or visual action
  - actor
  - target
- rubric_predicates
- grounding_check
- independent_verifier_result
- rubric_version
通用硬规则

一项只有满足以下条件才能成为 verified_level_4：

证据可定位
引文或视觉事件必须落在候选片段时间范围内；重复引用同一句话不算两份证据。

事件闭合
至少满足下列之一：

一个完整的“动作/发言 → 对方反应或结果”链；

两个不重叠的独立证据原子。

这样不会因为要求“两段证据”而误杀一个本身完整的单一高潮。

主张蕴含检查
第二个验证步骤只判断“这些证据是否足以满足 level 4 的 rubric”，不看原始分数，也不重新做综合评分。

验证失败直接封顶为 3
不是 4 - uncertainty_penalty，而是该 OR 路径根本不激活。

原始证据和验证结果必须可回放
不能只存一句“关系强烈”。必须能定位到具体视频和转录。

relationship_interaction=4 的具体合同

建议至少要求：

存在明确的定向互动：谁对谁做了什么或说了什么；

存在对方回应、关系后果或关系意义的明确揭示；

该互动是片段的主要 beat，不是背景闲聊；

结论不依赖直播外 CP lore、标题先验或纯弹幕脑补；

证据构成一条闭合互动链，或者有两个独立互动节点。

例如，“两个人同时在场、互相说了一句话”最多是 2 或 3；“她主动站队某人，对方回应，并由此改变当局互动”才有资格成为 4。

其他轴也要有轴专属合同

stance=4：必须有明确命题/选择，以及承诺、坚持、代价或后续行动；单纯提高音量不算。

audience=4：必须有可观察的观众驱动信号，以及主播因该信号改变表演；仅“弹幕很多”不够。

persona_reversal=4：必须引用版本化的人设基线；没有基线证据，不能仅凭模型印象认定“反差”。

comedic_payoff=4：需要可定位的 setup/payoff、误解揭示或明确反应；单句听起来有趣但没有落点，不应自动是 4。

最实际的验证策略

只对“某项 level 4 且准备单轴过门”的候选触发额外验证，而不是所有候选都双审：

首次评分出现 level 4
    ↓
独立、盲化的二次证据验证
    ↓
PASS → verified_level_4
FAIL/AMBIGUOUS → cap to level 3

这会把额外成本集中在真正改变决策的边界样本上。

3. 必要条件与卖点 OR 轴如何分层

建议明确分成四个不同字段，不再拿 tier 承担质量状态：

topic_tier             # 1/2/3，只描述题材类型
eligibility_status     # PASS / NEEDS_RECUT / REJECT
quality_score          # 内容自身质量
selection_score        # 经过当天疲劳后的选择效用
Gate 层

按现有 rubric，至少应有：

self_contained≥2

否则：

首先进入 NEEDS_RECUT，尝试向前后扩片或加必要字幕；

无法修复则 REJECT；

不允许进入任何 OR 路径。

关键点：不要把它改成 tier3。

一条内容完全可以是：

tier=1
basis=关系链
eligibility=REJECT
reason=self_contained_failed

这才符合“tier 与质量正交”。

comedic_payoff≤1 不应当是全局 gate

你现有的：

self_contained <= 1 OR comedic_payoff <= 1
    → force tier3

存在两个问题：

它破坏了 tier 的正交定义；

它会误杀严肃的关系、立场或 CP 站位片段。

正确处理应该是：

comedic_payoff<=1：禁用 comedy 路径；

关系、立场、观众驱动等路径仍可成立。

只有当产品定义明确要求所有短视频都必须有落点时，才应建立全局 gate；但这时维度应改名为更一般的 event_closure 或 narrative_payoff，而不是 comedic_payoff。严肃关系片可以有事件闭合，但不必搞笑。

Q=intrinsic quality
E=Q−F(当天题材状态)

配额和席位使用 E，质量分析使用 Q。

还要防止候选通过选择另一条路径逃避疲劳。例如一条片既是“关系链”又有笑点，不能因为关系链今天发多了，就把 winning path 写成 comedy 来规避惩罚。

具体做法：

在 OR 评分前，根据题材 basis、实体关系和语义相似度冻结 fatigue_key；

多标签时按预先声明的规则处理，例如取所有适用 bucket 中的最大疲劳惩罚，或使用一个不可由 winning path 改写的复合 bucket；

不允许评分器自己选择惩罚最小的标签。

6. OR 门是否本身就是错方向

纯维度 OR 是错方向；语义路径 OR 是正确方向。

直接做：

max(stance, audience, relationship, reversal, comedy)

会把粗粒度的 level 4 变成过强的单点开关，而且不同维度并不等价。

“游戏场单独调 profile”可以缓解当前案例，但不是完整解法：

它仍然是补偿性加权和；

下一次还会出现访谈场、联动场、杂谈场、比赛场各自的 profile；

场景分类错误会直接改变评分；

同一场游戏里仍然可能有“关系特别强”和“笑点特别强”两类完全不同的优质片。

场景 profile 更适合：

调整先验；

调整证据 rubric；

调整疲劳分桶；

做监控分层。

不适合作为核心聚合语义。

另外，全池最高只有 82.75 并不能单独证明评分器错了。如果第六席本来可以空缺，那么“无人达到85”可能是合法结果。真正支持改模型的证据应当是：盲审确认 A—D 中确实有片子值得第六席，但 v1 系统性拒绝它们。

问题1最没把握的部分

H、中心性奖励 b 和最终席位阈值的具体数值；没有历史盲标数据，不能可靠拍定。

哪些轴应允许单独触发 OR，尤其是 persona_reversal 和 comedic_payoff；这取决于产品是否把纯反差或纯笑点视为独立发布理由。

3. 如果不拆，有什么替代手段

在当前事实下，不存在符合现有治理规则的长期“不拆方案”。下面只能作为拆解前的临时风险控制：

把模式 × 封面路线整理成显式 16 格决策表；

为所有合法格和非法格建立契约测试；

对每个 fail-closed 条件逐一制造失败，断言：

不返回草稿；

不发生 commit；

不触发不允许的 fallback；

记录副作用调用序列，而不仅比较最终 JSON；

冻结函数，不允许再加入模式、路线或 gate；

使用 branch coverage，但不能把“分支覆盖100%”视作充分条件；

对安全判断做条件独立测试，接近 MC/DC：每个条件单独翻转时，都能证明其决策影响。

必须回头拆的条件包括：

第三次抬高行数；

新增第五种投稿模式；

新增封面路线；

修改任何授权、证据、哈希或 fail-closed 判断；

现有 16 格行为无法清楚枚举；

需要在多个分支重复修复同一个 bug。

但这些条件中，“第二次上调并已有明确禁止注释”已经发生，因此不是未来条件，而是当前触发器。

4. 130 个局部变量说明什么

在这个函数里，130 个局部变量比单纯的 597 行更强烈地说明结构有问题。

它通常表示：

函数在充当一个没有显式类型的工作流对象；

不同阶段的中间状态都平铺在一个作用域中；

模式和路线通过“某些局部变量是否已赋值”隐式编码；

存在较强的时间耦合：变量必须在正确分支和正确顺序中产生；

恢复或 fallback 路径容易读到错误阶段、错误模式或旧值；

大量变量本来应当属于 DraftPlan、MetadataArtifacts、CoverArtifact、EvidenceBundle 等阶段对象。

不过要区分：

130 个词法局部名；

某一点同时存活的峰值 live variables。

如果大多数变量只存在于互斥分支中，130 会夸大瞬时认知负担。但在 40 个分支和多模式恢复逻辑下，它仍然强烈暗示状态空间没有被显式建模。

更准确的风险指标排序是：

隐式状态数量和不变量>峰值活跃变量>分支交叉积>总局部名>行数

所以答案是：是，130 个局部变量在这里比“597 行”更值得警惕；但真正的问题不是数字本身，而是这些变量跨越了多少阶段和失败域。

不要用一个 PublishContext 大包把 130 个局部变量全部变成 130 个可变字段。那只是把局部变量问题升级成共享可变状态问题。阶段输出应当是小型、不可变、语义明确的数据结构。

5. 最常见和最危险的拆坏方式
最常见的结构性失败

把原函数机械切成十个 helper，但所有 helper 都读写同一个巨大可变 ctx：

Python
Run

_prepare_cover(ctx)
_bind_evidence(ctx)

代码行数下降了，但：

执行顺序仍然隐式；

字段是否存在仍由分支决定；

helper 之间耦合更难搜索；

原来的单体函数变成了分布式单体。

这不算成功拆分。

这个函数里最危险的正确性失败

在 helper 边界上合并了失败语义，把原来的 fail-closed 变成 fallback 或部分成功。

典型例子：

Python
Run
try:
    cover = prepare_cover(...)
except Exception:
    cover = fallback_cover(...)

如果 prepare_cover() 内部同时可能抛出：

服务超时；

授权无效；

哈希不匹配；

回执缺失；

文件损坏；

那么一次看似合理的提取就可能让安全失败走进普通降级路线。

这是你最应该防的一种。

必须建立的防线

失败类型分层
只有白名单中的 recoverable 错误允许 fallback。

使无效状态不可表示
commit 只接受 SealedDraft，不接受一堆布尔值和可选字段。

差分测试旧实现与新实现
对固定 fixture、固定时钟、固定随机源和模拟外部系统，比较：

返回值；

异常类型；

是否创建草稿；

外部调用及顺序；

文件和哈希；

重放第二次的行为。

负路径优先
每个 fail-closed gate 都至少有一个独立失败测试，并断言没有不可逆副作用。

先行为保持，后功能改动
拆分提交里不顺便“清理逻辑”“改 fallback”“简化授权”；否则无法判断差异来自重构还是语义变化。

禁止宽泛捕获跨越安全边界
orchestrator 不应有覆盖整个阶段的 except Exception。

拆解完成的验收判据

至少应满足：

4 种模式 × 4 种封面路线全部有显式测试；

所有非法组合在不可逆副作用前失败；

每个 fail-closed gate 有负向测试；

只有明确的 cover recoverable failure 能进入 cover fallback；

旧实现与新实现的 fixture 差分结果一致；

重放两次不产生重复不可逆效果；

原 orchestrator 明显低于 300，建议低于 120；

没有新建 300 行以上 helper；

原模块净下降，而不是只把函数改名或塞进类中；

欠账账本数字下降，不再批准 597 作为新基线。

问题2最没把握的部分
